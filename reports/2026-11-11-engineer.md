# Engineer 2026-11-11

1 ticket: `Scan StockAnalysis_Team_ScanOps exited with an error on 2026-11-10 and could not be re-run validly`.

## Ticket: ScanOps false-flagged itself on 2026-11-10

### Cause — a false positive from the sleep/wake, `tools/scan_ops.py:94`
This is the same 2026-11-10 sleep event the last run already diagnosed for QuoteClose. The machine was asleep
from ~10:00 to ~15:30 PT (`state/logs/2026-11-10-scan_ops.log` jumps 10:00:04 → 15:30:35; two overlapping
catch-up instances logged at 15:30:35 and 15:30:39). Evidence it was NOT a real ScanOps crash:
- every scan_ops run on 11-10 and 11-11 logged cleanly (`... scan_ops: N event(s)`); no Traceback in
  `state/logs/scan_ops_task.log`;
- ScanOps ran every 10 min fine before the sleep (to 10:00) and after the wake (from 15:30);
- the 15:30:35 run's single event was QuoteClose, not ScanOps.

The pre-sleep ScanOps run was terminated by the system, leaving a non-OK `LastResult`. A post-wake snapshot
(`scheduled_tasks()`, taken once at the top of the check) caught the ScanOps task with that stale terminated
result and a `State` no longer `"Running"`. The self-skip guard at `scan_ops.py:94`
(`... or t["State"] == "Running": continue`) only fires when the snapshot shows `"Running"` — it can't catch the
stale non-Running case — so scan_ops evaluated its own row, saw `failed` (`scan_ops.py:98`), and because ScanOps
has `retry_until: null` (never re-run automatically) it went straight to the give-up branch and recorded an issue
(`scan_ops.py:120-125`). That became the false "ScanOps exited with an error" ticket.

A genuine ScanOps failure is still caught independently by `ops_monitor.check_tasks` (`tools/ops_monitor.py:92-95`),
which runs once per dispatch when the machine is awake and the transient terminated state has cleared — which is
why ops_monitor did NOT alert on 11-10. So scan_ops's own 10-min self-poll adds only false positives, never a
true positive ops_monitor would miss.

### Fix
`tools/scan_ops.py`: added `OWN_TASK` and a `if name == OWN_TASK: continue` after the drift check, so scan_ops
no longer judges its own run outcome (it keeps the drift/disabled/missing checks, which are still meaningful).
This is removing a structurally-unreliable check, not muting a real one: scan_ops cannot observe its own
completed-run result consistently (it is itself the running instance, or sees a stale post-sleep result), and
ops_monitor remains the reliable watchdog for ScanOps.

### Proven
`tests/test_eng_scan_ops_self_flag.py` feeds a post-sleep snapshot (ScanOps: recent LastRun, non-OK LastResult,
State "Ready") plus a genuinely-failed second job, and asserts scan_ops files NO ticket against itself while still
recording the real failure. Fails on the old code (self-ticket filed), passes on the new. `engineer.py check`:
guard OK, full suite 79 passed.

The 11-10 issue itself needs no cleanup: `engineer.py prepare()` already advanced `last_run` to 2026-11-11, so
the 11-10 entry is outside the next dispatch's window and won't re-fire; it ages out of scan_ops.json's 7-day
`issues` window on its own.

## Proposals for the user
None new. The underlying trigger is the same machine-asleep condition from 2026-11-10; the standing proposals in
`reports/2026-11-10-engineer.md` (wake-to-run / keep-awake on the frozen Quote tasks) still stand. This fix makes
the Scan Operator stop raising a false self-failure when that happens, independent of those.
